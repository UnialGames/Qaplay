# qaplay 작업 계획 (v0.1)

> 기준 문서: [requirements.md](requirements.md). 이 문서는 "무엇을"이 아니라 "어떤 순서로, 어디까지 되면 끝인지"만 다룬다.

## 진행 원칙

- 단계마다 샘플 프로젝트에서 직접 돌려 볼 수 있는 결과물로 끝낸다. 돌려 볼 수 없으면 그 단계는 끝난 것이 아니다.
- [미정] 항목은 미리 다 정하지 않는다. 그 항목이 필요한 단계를 시작할 때 정하고, 정한 내용을 requirements.md에 반영한다.
- 뒤 단계일수록 계획을 거칠게 둔다. 앞 단계를 만들면서 알게 되는 것이 많으므로, 세부 계획은 그 단계에 도착했을 때 쓴다.
- 단계 하나를 브랜치 하나, PR 하나로 묶는다.
- 에이전트(C#), 러너(C#), Python 클라이언트는 프로토콜 명세만 보고 구현한다. 명세에 없는 동작이 필요하면 명세를 먼저 고친다.

## 저장소 구조

```
docs/        요구사항, 작업 계획
protocol/    프로토콜 명세 (메시지 형식, 명령 목록, 예시 JSON)
unity/       Unity 6.3 프로젝트 (개발용 겸 샘플)
  Packages/com.qaplay.core/   에이전트, UI 어댑터, 에디터 도구
runner/      .NET CLI 러너 (명령 이름: qaplay)
python/      Python 클라이언트 라이브러리 (패키지 이름: qaplay)
```

UPM 설치는 git URL에 `?path=unity/Packages/com.qaplay.core`를 붙이는 방식으로 한다.

requirements.md의 "개발 순서 (안)"과 다른 점은 두 가지다.

- CI 기본 조건(종료 코드, JUnit XML)을 3단계에 넣었다. 러너를 만들 때 같이 넣으면 비용이 거의 없고, 이후 단계의 검증을 CI로 돌릴 수 있다.

## 앞 단계 상세

### 0단계: 저장소 뼈대와 프로토콜 명세 v0

만들 것

- `.gitignore`(Unity, .NET, Python), `LICENSE`(MIT), `README.md`
- `protocol/README.md`: 메시지 봉투(요청, 응답, 이벤트 공통 필드), 길이 접두어 규칙, 버전 협상, 오류 형식
- 명령 v0: `hello`(버전 협상), `dump`(UI 계층), `find`(조건 검색), `tap`, `wait`, `get`(게임 값 조회)
- UI 계층 덤프 포맷: 요소 한 개의 필드(이름, 타입, 텍스트, 화면 영역, 가시성, 누를 수 있는지, 자식)

이 단계에서 정한 것 (상세는 [프로토콜 명세](../protocol/README.md))

- 좌표 표기: 정규화 0~1만 사용, 왼쪽 위 원점. 픽셀은 `screen` 크기를 곱해 구함
- 조건 검색 문법: `name`, `type`, `text`, `id`는 정확히 일치, 부모 범위는 `within`, 순번은 `index`. 하나여야 하는 자리에서 여러 개가 걸리면 고르지 않고 오류
- 메시지 봉투: `req`/`res`/`evt` 세 종류, 오류는 문자열 코드
- 요소 종류와 글자: uGUI와 UI Toolkit이 같은 셀렉터로 찾아지도록 공통 종류 이름을 쓰고, 글자 없는 버튼은 자손 글자를 가짐

### 1단계: 에디터 내 에이전트

만들 것

- Unity 프로젝트와 `com.qaplay.core` 패키지 (asmdef, define symbol로 QA 빌드 분리)
- 명령 계층: 0단계의 명령을 프로세스 내 함수 호출로 실행
- uGUI 어댑터: 계층 덤프, 조건 검색, 화면 영역 계산
- 입력 주입: Input System 가상 터치로 탭. 가려졌거나 화면 밖이면 "누를 수 없음"과 원인 반환
- 대기 조건: 요소 나타남, 사라짐, 텍스트 일치
- 샘플 씬: 버튼, 팝업, 목록이 있는 화면

검증: Unity Test Framework의 PlayMode 테스트로 샘플 씬을 조작한다. 소켓은 아직 없다.

이 단계에서 정한 것

- QA 빌드 분리: Scripting Define Symbols에 `QAPLAY`가 있는 빌드에만 에이전트가 들어간다. 에디터에서는 심벌 없이도 항상 동작한다
  - 출시 빌드에 남는 것은 게임 코드가 참조하는 `Qaplay.Api` 하나다(고유 ID 컴포넌트 `QaplayId`, 게임 값 등록 `GameValues.Register`). 등록 호출은 출시 빌드에서 컴파일되지 않는다
  - 나머지 어셈블리는 asmdef의 `defineConstraints`에 `QAPLAY || UNITY_EDITOR`를 건다. 이 조건을 빼먹은 어셈블리가 있으면 빌드를 시작할 때 실패한다
- 대기의 기본 제한 시간: 10초. 프로토콜의 `timeoutMs`는 필수로 두고, 적지 않았을 때 러너와 Python 클라이언트가 이 값을 넣는다
- 결정성에서 도구가 직접 처리할 항목: 누르기 전 자동 대기, Unity 기본 랜덤(`UnityEngine.Random`) 시드 고정
  - 넣지 않기로 한 것: 움직임이 멈출 때까지 대기, 시간 배율 제어
  - 자동 대기는 `tap`의 `timeoutMs`로, 시드 고정은 `seed` 명령으로 넣었다

### 2단계: 기록/재생과 YAML 규칙

만들 것

- 입력 기록: 터치를 받은 요소를 조건 검색 표기로 바꿔 순서대로 저장
- YAML 규칙 파일 읽기와 실행 (에디터 내)
- 사전 검증기: 조건에 걸리는 요소가 없거나 여럿인 경우 검출

조각 순서

1. 규칙 파일 문법 정하기 ([규칙 파일 명세](rules.md))
2. 규칙 읽기: YAML을 명령 목록으로 바꾸고 문법 오류를 알림
3. 규칙 실행: 명령을 에이전트에 보내 통과와 실패를 판정 (에디터 내)
4. 사전 검증기: 규칙의 셀렉터를 현재 화면에 대어 없음과 여럿을 찾음
5. 입력 기록: 사람이 누른 요소를 셀렉터로 바꿔 규칙 파일로 저장

이 단계에서 정한 것 (상세는 [규칙 파일 명세](rules.md))

- 명령 이름과 구조는 Maestro를 따른다. v0 명령은 `tapOn`, `assertVisible`, `assertNotVisible`, `assertValue`, `seed`
- 글자는 정확히 일치로 본다. 모르는 명령과 머리말 필드는 실행 전에 오류로 알린다
- 기록할 때 요소를 적는 순서: 고유 ID, 이름, 글자. 하나로 정해지지 않으면 범위(`within`), 그다음 순서(`index`)를 덧붙인다
- YAML은 라이브러리 없이 직접 읽는다. 규칙 파일 명세에 나온 모양(한 줄짜리 `{ }`)만 읽고, 여러 줄로 들여 쓴 중첩 같은 나머지 문법은 오류로 알린다
- 규칙을 읽는 쪽이 명령을 프로토콜 요청(`cmd`, `args`)으로 미리 바꿔 둔다. 실행하는 쪽은 보내고 판정만 한다
- 규칙을 실행하는 쪽은 "명령 하나를 보내고 응답을 받는 길"만 넘겨받는다. 에디터에서는 프로세스 안의 에이전트, 3단계의 러너에서는 소켓이 그 길이다

- 사전 검증기는 지금 화면 하나만 본다. 요소는 `find`의 `resolves`로, 게임 값은 `get`으로 확인한다
- 입력 기록은 탭만 다룬다. UI 입력 모듈의 누르기 입력을 함께 듣고, 누른 순간의 화면에서 셀렉터를 정한다
- 에디터 창(`qaplay > Rules`) 하나에 기록, 저장, 사전 검증, 실행을 둔다

검증

- PlayMode 테스트가 샘플 화면에서 터치를 기록해 YAML로 만들고, 640x480에서 기록한 것을 540x960에서 재생해 통과한다
- 에디터 창은 사람이 직접 눌러 확인한다(자동 테스트 없음)

다음 단계로 넘긴 것

- 탭 이외의 조작(글자 입력, 스크롤, 끌기, 뒤로 가기)의 기록과 재생. 에이전트 명령부터 필요하다
- 씬과 프리팹의 정적 검사(요구사항 9번 [보완])
- 여러 화면을 넘겨 가며 하는 사전 검증

### 3단계: 소켓, 러너, Python 클라이언트

만들 것

- 에이전트 TCP 서버: 길이 접두어 + JSON, 생존 신호(프레임 번호)
- 러너 CLI: 기기 목록, adb forward, 연결, 규칙 파일 실행, 종료 코드, JUnit XML
- Python 클라이언트: `find`, `tap`, `wait`, `get`을 감싼 얇은 라이브러리

조각 순서

1. 에이전트 TCP 서버 (`AgentServer`)
2. 러너 CLI: 접속, 규칙 실행, 종료 코드, JUnit XML (`qaplay run`, `qaplay check`)
3. 재시도와 불안정 판정
4. 러너의 중계와 Python 클라이언트 (`qaplay serve`, `python/qaplay`)
5. Android 기기 목록과 포트 연결 (`qaplay devices`, `--device`)

이 단계에서 정한 것

- 러너와 Python 스크립트의 연결: Python도 러너의 localhost 포트(기본 27276)에 게임과 같은 프로토콜로 접속하고, 러너가 게임으로 중계한다. 프로토콜은 하나로 유지된다
  - 지금의 중계는 바이트를 그대로 옮긴다. 러너가 메시지를 들여다봐야 하는 4단계(크래시 복구)에서 프레임 단위로 바꾼다
- 재시도 기본값: 1번. 다시 돌려 통과하면 불안정(flaky)이고 종료 코드는 성공이다. `--retries N`으로 바꾼다
- 에이전트는 게임이 시작되면 `127.0.0.1:27275`에서 자동으로 기다린다(에디터의 Play와 QA 빌드). 포트는 실행 인자 `-qaplay-port`나 환경 변수 `QAPLAY_PORT`로 바꾼다
- 러너의 종료 코드: 0 모두 통과(불안정 포함), 1 실패가 있음, 2 사용법이 틀렸거나 게임에 닿지 못함
- 러너는 .NET 10으로 만든다. 규칙을 읽고 실행하고 검증하는 코드는 Unity 패키지의 파일을 그대로 가져다 쓴다(두 벌을 만들지 않는다)
- 러너가 게임 없이 확인할 수 있는 로직은 `qaplay selftest`로 검사하고, 게임을 거치는 전체 경로는 PlayMode 테스트(`RunnerTests`)가 러너와 Python을 실제 프로세스로 띄워 확인한다

검증

- PlayMode 테스트가 러너(`qaplay.exe`)와 Python 스크립트를 실제 프로세스로 띄워, 소켓을 거쳐 샘플 화면을 다루게 한다: 통과, 실패, 불안정, 폴더 실행, 사전 검증, 연결 실패, Python 중계
- Windows QA 빌드를 띄워 같은 명령을 돌렸다: `qaplay run`(통과), `qaplay check`, `qaplay serve -- python`(통과), 실패하는 규칙(종료 코드 1). 창에 포커스가 없는 상태에서 가상 터치가 들어갔다
- Android 기기는 연결된 것이 없어 확인하지 못했다(미실측 목록)

다음 단계로 넘긴 것

- 다시 돌리기 전에 게임을 처음 상태로 되돌리기(앱 재시작, 상태 초기화). 지금은 앞 시도가 남긴 상태에서 이어서 돈다
- 생존 신호로 프리징을 판정하기. 에이전트는 신호를 보내고, 러너는 아직 읽고 버린다
- Wi-Fi 접속과 토큰 검사. 지금은 그 기기 안에서 오는 접속만 받는다
- 사람이 읽는 상세 리포트. 지금은 콘솔 출력과 JUnit XML뿐이다

### 4단계: 크래시 감지와 복구

조각 순서

1. 예외 이벤트(`exception`)와 샘플의 문제 버튼 3개(예외, 크래시, 프리징)
2. 러너의 판정: 예외, 크래시(연결 끊김), 프리징(프레임 번호 멈춤)
3. 러너가 게임을 띄우고 다시 띄우기(`--app`, `--package`), 게임 로그 수집(`--artifacts`)
4. Windows QA 빌드로 전체 검증

이 단계에서 정한 것

- 예외, 크래시, 프리징이 난 규칙은 확인 명령이 모두 통과했더라도 실패이고, 다시 돌리지 않는다. 가끔만 나더라도 버그이므로 재시도로 덮지 않는다
- 프리징 기준은 10초. 생존 신호의 프레임 번호가 그만큼 그대로이면 프리징이다. `--freeze-seconds`로 바꾼다
- 명령의 제한 시간이 지나고도 10초 더 응답이 없으면, 프레임이 돌고 있더라도 프리징으로 본다(요구사항의 "응답 타임아웃")
- 크래시와 프리징의 구분: 죽는 중인 게임은 크래시 기록을 쓰는 동안 연결이 끊기지 않아 프리징처럼 보인다. 러너가 띄운 게임이면 게임의 로그에 남은 크래시 표시(`Crash!!!` 등)로 구분한다
- 복구는 러너가 게임을 직접 띄운 경우에만 한다. 이미 떠 있는 게임이나 에디터에 붙은 경우에는 다시 띄울 수 없어 남은 규칙이 `not_connected`로 실패한다
- 러너가 띄운 게임이면 다시 돌릴 때도 게임을 새로 띄운다. 3단계에서 넘긴 "다시 돌리기 전에 처음 상태로"가 이것으로 해결된다
- IL2CPP 심볼리케이션은 기기 검증이 가능할 때로 미룬다. 지금은 게임이 남긴 로그와 스택을 원문 그대로 저장한다

검증

- `qaplay selftest`: 가짜 게임으로 예외, 크래시, 프리징, "오래 걸리지만 프레임은 도는 응답"을 구분하는지 검사한다
- PlayMode 테스트: 예외 이벤트가 소켓으로 오는지, 예외가 난 규칙이 실패하고 다시 돌지 않는지
- Windows QA 빌드를 러너가 직접 띄워 규칙 6개를 돌렸다: 통과, 예외, 크래시(종료 코드 -1073741819, 로그 저장, 재실행), 프리징(로그 저장, 재실행), 그 뒤의 규칙 통과, 다시 돌릴 때 새 게임에서 시작
- Python 스크립트도 같은 게임으로 돌렸다: 정상 스크립트는 종료 코드 0, 크래시를 내는 스크립트는 종료 코드 1과 로그 저장

다음 단계로 넘긴 것

- Python 스크립트 쪽의 예외와 프리징 판정. 중계가 아직 바이트를 그대로 옮기므로, 스크립트는 크래시만 알 수 있다(연결 끊김). 프레임 단위 중계는 필요해질 때 만든다
- 크래시 건을 버그 제보 형식으로 자동 등록(5단계)
- 크래시 직전 조작 이력을 러너 쪽에 실시간으로 남기기(5단계의 조작 이력과 함께)
- OOM 강제 종료의 추정(7단계의 메모리 기록과 함께)
- Android의 tombstone 수집. 지금은 logcat만 남긴다

### 5단계: 버그 제보와 회귀 편입

조각 순서

1. 게임 안의 상시 조작 이력과 제보 저장 (`BugReporter`, 명령 `report`, `reports`, `reportGet`, `reportDelete`)
2. PC로 가져오기와 버그 관리 명령 (`qaplay bugs pull / report / list / show / set / delete`)
3. 회귀 규칙 만들기와 해결 확인 (`qaplay bugs promote / verify`)
4. 예외, 크래시, 프리징의 자동 등록과 같은 버그 묶기

이 단계에서 정한 것 (상세는 [버그 리포트](bugs.md))

- 범위: 제보, 가져오기, 관리 명령, 회귀 규칙, 자동 등록까지 만든다. 확인 대기 목록, 합치기와 나누기, 수정 이력, 재현율은 뒤로 미룬다
- 게임에서 건 제보는 제목을 받지 않고 바로 저장한다. 제목과 설명은 PC로 가져온 뒤에 적는다. 플레이 흐름이 끊기지 않고, 입력 창이 게임 UI와 섞이지 않는다
- 제보를 거는 방법: 키보드 F12, 세 손가락으로 1초 누르기, `qaplay bugs report`, Python의 `game.report()`
- 조작 이력은 Play 동안 늘 쌓는다(최근 5분, 최대 200개). 2단계의 입력 기록기가 늘 듣게 바꿨다
- 버그를 "해결됨"으로 바꾸는 것만으로는 아무것도 실행하지 않는다. `qaplay bugs verify`가 회귀 규칙을 돌려 통과하면 `verified`, 실패하면 `open`으로 바꾼다
- 같은 버그의 기준: 예외는 종류와 맨 위 호출 지점, 크래시와 프리징은 규칙 파일. 크래시의 네이티브 스택은 심볼리케이션과 함께 본다
- 리포트 삭제 시 연동 이슈를 어떻게 할지는 연동을 만드는 9단계에서 정한다. 지금의 삭제는 PC의 폴더만 지운다

검증

- PlayMode 테스트: 제보 명령 4개, F12, 세 손가락 누르기, 그리고 러너를 실제 프로세스로 띄워 "제보 → 가져오기 → 제목 적기 → 회귀 규칙 → 해결 확인 → 다시 실패하면 회귀로 다시 열림"과 "예외의 자동 등록과 묶기"
- `qaplay selftest`: 저장소의 번호 매기기, 같은 버그 가리기, 다시 열기
- Windows QA 빌드: 화면이 담긴 제보를 가져오고, 크래시가 로그와 함께 자동 등록되는지

### 5단계

- [ ] 에디터에서 탭한 버튼이 한 번 더 눌리던 현상: 원인을 찾아 고쳤다. 에디터에서 다시 나지 않는지만 남았다
  - 본 것: 2026-11-25 22:49의 전체 실행에서 `Run_FailingRule_ExitsWithOneAndSaysWhy`가 `Unhandled log message: '[Exception] InvalidOperationException: sample exception from ExceptionButton'`로 실패했다. 이 테스트는 예외 버튼을 누르지 않고, 바로 앞 테스트가 누른다
  - 원인: 주입기가 탭하는 동안 마우스를 껐다가 다시 켰는데, Input System은 장치를 다시 켤 때 현재 상태를 다시 받아 온다. 그때 사람이 마우스 버튼을 누르고 있었다면 "눌림"이 새로 들어온다. UI 입력 모듈은 끝난 터치의 포인터 기록을 한 프레임 더 들고 있고, 그 사이에 온 마우스 입력은 그 기록을 물려받는다(위치는 터치의 위치 그대로). 그래서 마우스의 눌림이 방금 탭한 자리에서 처리되고, 버튼을 뗄 때 그 요소가 한 번 더 클릭됐다
  - 재현: `TapTests.Tap_IsNotRepeatedByAMouseButtonPressedAroundIt`. 고치기 전에는 골드가 `1,000`(두 번 구매), 고친 뒤에는 `1,100`
  - 고친 것: 마우스를 껐다 켜지 않는다. 탭하는 네 프레임 동안 마우스와 펜의 입력을 버리고, 끝난 터치의 기록이 지워진 뒤에 다시 받는다
  - 고치다가 만든 문제와 그 원인: 처음 고친 판은 마우스를 막자마자 터치를 넣었는데, 에디터에서 화면을 새로 만든 직후의 탭이 전달되지 않았다(골드가 `1,200` 그대로). 화면을 새로 만든 첫 프레임에는 EventSystem이 입력 모듈을 바꾸느라 포인터를 처리하지 않아, 새 모듈이 받은 마우스 위치의 "이번 프레임에 바뀜" 표시가 다음 프레임까지 남는다. 그 프레임에 터치가 들어오면 모듈이 마우스를 택하고 터치를 버린다. 그래서 마우스를 막은 뒤 한 프레임을 보내고 터치를 넣는다
  - 배치 모드에서는 둘 다 보이지 않는다(마우스와 펜 장치가 없다). 입력을 건드리는 변경은 창 모드 에디터(`-batchmode` 없이 `-runTests`)로도 돌린다
  - 확인하지 못한 것: 그날의 실패가 정말 이 경로였는지(그 순간 마우스 버튼을 누르고 있었는지 기록이 없다). 에디터에서 테스트가 도는 동안 다른 창을 여러 번 눌러 보고, 다시 나지 않는지 본다
  - 2026-11-26에 사람이 쓰는 에디터에서 본 것: 구매 7번이 든 12줄짜리 규칙을 처음부터 세 번 재생했고(Free Aspect, 4K, `bugs verify`) 골드는 세 번 모두 `1,200`에서 `500`으로 정확히 줄었다. 탭하는 동안 마우스 버튼을 누르고 있는 조건은 손으로 만들지 않았다
- [ ] 탭 뒤에 마우스를 움직이지 않고 누른 클릭의 위치. UI 입력 모듈은 터치가 들어오면 마우스의 포인터 기록을 지우고, 그 뒤 마우스가 움직이지 않은 채 눌리면 화면 왼쪽 아래 구석 (0, 0)에서 처리한다(Input System 1.14.2의 동작이고, 도구가 만든 것이 아니다). 그 구석에 클릭을 받는 요소(전체 화면을 덮는 버튼 등)가 있는 게임에서, 규칙을 돌린 직후 에디터의 다른 창을 제자리에서 누르면 그 요소가 눌릴 수 있다. 샘플에는 그 자리에 요소가 없어 확인하지 못했다
- [x] 실제 키보드의 F12로 제보하기. 2026-11-25에 에디터에서 확인됐다: 제보 7건이 저장됐고, 각각 1920x1080 화면(약 305KB), 직전 조작, 로그가 들어 있었다

### 4단계

- [ ] Android 기기에서의 크래시와 프리징 복구. 기기가 없어 코드만 만들었다
  1. `qaplay run <규칙 폴더> --device <시리얼> --package <패키지 이름>`으로 러너가 앱을 띄우는지 본다
  2. 샘플의 크래시, 프리징 버튼을 누르는 규칙이 각각 `crash`, `freeze`로 나오는지 본다
  3. `--artifacts` 폴더에 logcat이 저장되고, 앱이 다시 떠서 다음 규칙이 이어지는지 본다
  - 함께 볼 것: 크래시와 프리징의 구분에 쓰는 logcat의 표시(`Fatal signal`, `FATAL EXCEPTION`)가 실제로 남는지, IL2CPP 빌드의 스택이 어떻게 보이는지(심볼리케이션을 이때 정한다)

- [x] 에디터에서 예외가 난 규칙을 사람이 쓰는 에디터 창으로 돌리는 것. 2026-11-26에 확인했다: 예외 버튼을 누르는 규칙이 `FAIL ... exception: InvalidOperationException`, 종료 코드 1로 끝났고 버그가 자동 등록됐다. 한 번 더 돌리니 새로 만들지 않고 `count`가 2가 됐다
- [ ] 로딩이 긴 실제 게임에서 프리징 기준 10초가 잘못 잡히지 않는지

  3. `qaplay run unity/Assets/Sample/Rules/shop.yaml --device <시리얼>`이 통과하는지 본다 (`adb forward`는 러너가 건다)
  4. `qaplay serve --device <시리얼> -- python python/examples/shop.py`가 통과하는지 본다
  - 함께 볼 것: 앱에 인터넷 권한이 들어갔는지(소켓을 열려면 필요하다. Unity가 자동으로 넣는 것으로 알고 있으나 확인하지 않았다), IL2CPP에서 에이전트 코드가 잘려 나가지 않는지
