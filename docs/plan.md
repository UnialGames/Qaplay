# qaplay 작업 계획 (v0.1)

> 기준 문서: [requirements.md](requirements.md). 이 문서는 "무엇을"이 아니라 "어떤 순서로, 어디까지 되면 끝인지"만 다룬다.

## 진행 원칙

- 단계마다 샘플 프로젝트에서 직접 돌려 볼 수 있는 결과물로 끝낸다. 돌려 볼 수 없으면 그 단계는 끝난 것이 아니다.
- [미정] 항목은 미리 다 정하지 않는다. 그 항목이 필요한 단계를 시작할 때 정하고, 정한 내용을 requirements.md에 반영한다.
- 뒤 단계일수록 계획을 거칠게 둔다. 앞 단계를 만들면서 알게 되는 것이 많으므로, 세부 계획은 그 단계에 도착했을 때 쓴다.
- 단계 하나를 브랜치 하나, PR 하나로 묶는다.
- 에이전트(C#), 러너(C#), Python 클라이언트는 프로토콜 명세만 보고 구현한다. 명세에 없는 동작이 필요하면 명세를 먼저 고친다.

## 저장소 구조

```
docs/        요구사항, 작업 계획
protocol/    프로토콜 명세 (메시지 형식, 명령 목록, 예시 JSON)
unity/       Unity 6.3 프로젝트 (개발용 겸 샘플)
  Packages/com.qaplay.core/   에이전트, UI 어댑터, 에디터 도구
runner/      .NET CLI 러너 (명령 이름: qaplay)
python/      Python 클라이언트 라이브러리 (패키지 이름: qaplay)
```

UPM 설치는 git URL에 `?path=unity/Packages/com.qaplay.core`를 붙이는 방식으로 한다.

requirements.md의 "개발 순서 (안)"과 다른 점은 두 가지다.

- CI 기본 조건(종료 코드, JUnit XML)을 3단계에 넣었다. 러너를 만들 때 같이 넣으면 비용이 거의 없고, 이후 단계의 검증을 CI로 돌릴 수 있다.

## 앞 단계 상세

### 0단계: 저장소 뼈대와 프로토콜 명세 v0

만들 것

- `.gitignore`(Unity, .NET, Python), `LICENSE`(MIT), `README.md`
- `protocol/README.md`: 메시지 봉투(요청, 응답, 이벤트 공통 필드), 길이 접두어 규칙, 버전 협상, 오류 형식
- 명령 v0: `hello`(버전 협상), `dump`(UI 계층), `find`(조건 검색), `tap`, `wait`, `get`(게임 값 조회)
- UI 계층 덤프 포맷: 요소 한 개의 필드(이름, 타입, 텍스트, 화면 영역, 가시성, 누를 수 있는지, 자식)

이 단계에서 정한 것 (상세는 [프로토콜 명세](../protocol/README.md))

- 좌표 표기: 정규화 0~1만 사용, 왼쪽 위 원점. 픽셀은 `screen` 크기를 곱해 구함
- 조건 검색 문법: `name`, `type`, `text`, `id`는 정확히 일치, 부모 범위는 `within`, 순번은 `index`. 하나여야 하는 자리에서 여러 개가 걸리면 고르지 않고 오류
- 메시지 봉투: `req`/`res`/`evt` 세 종류, 오류는 문자열 코드
- 요소 종류와 글자: uGUI와 UI Toolkit이 같은 셀렉터로 찾아지도록 공통 종류 이름을 쓰고, 글자 없는 버튼은 자손 글자를 가짐

### 1단계: 에디터 내 에이전트

만들 것

- Unity 프로젝트와 `com.qaplay.core` 패키지 (asmdef, define symbol로 QA 빌드 분리)
- 명령 계층: 0단계의 명령을 프로세스 내 함수 호출로 실행
- uGUI 어댑터: 계층 덤프, 조건 검색, 화면 영역 계산
- 입력 주입: Input System 가상 터치로 탭. 가려졌거나 화면 밖이면 "누를 수 없음"과 원인 반환
- 대기 조건: 요소 나타남, 사라짐, 텍스트 일치
- 샘플 씬: 버튼, 팝업, 목록이 있는 화면

검증: Unity Test Framework의 PlayMode 테스트로 샘플 씬을 조작한다. 소켓은 아직 없다.

이 단계에서 정한 것

- QA 빌드 분리: Scripting Define Symbols에 `QAPLAY`가 있는 빌드에만 에이전트가 들어간다. 에디터에서는 심벌 없이도 항상 동작한다
  - 출시 빌드에 남는 것은 게임 코드가 참조하는 `Qaplay.Api` 하나다(고유 ID 컴포넌트 `QaplayId`, 게임 값 등록 `GameValues.Register`). 등록 호출은 출시 빌드에서 컴파일되지 않는다
  - 나머지 어셈블리는 asmdef의 `defineConstraints`에 `QAPLAY || UNITY_EDITOR`를 건다. 이 조건을 빼먹은 어셈블리가 있으면 빌드를 시작할 때 실패한다
  - 2026-11-26에 Player Settings(`ProjectSettings.asset`)에 `QAPLAY`를 직접 적고 빌드 스크립트의 추가 심벌 없이 Windows 빌드를 만들어 확인했다: QA 어셈블리 다섯 개가 들어갔고 `shop.yaml`과 `rapid-buy.yaml`이 통과했다
  - IL2CPP 빌드에서는 에이전트가 빠져 있었다(같은 날 Android IL2CPP 빌드로 확인). 에이전트 어셈블리는 게임 코드가 참조하지 않고 `RuntimeInitializeOnLoadMethod`로만 시작되는데, 코드 스트리핑은 아무도 참조하지 않는 패키지 어셈블리를 그 표시도 보지 않고 통째로 뺀다. `Qaplay.Agent`에 `[assembly: AlwaysLinkAssembly]`를 붙여 고쳤다. Windows Mono 빌드는 스트리핑을 하지 않아 드러나지 않았다
  - 2026-11-28에 Windows IL2CPP QA 빌드로도 확인했다(고친 뒤의 코드): 에이전트 어셈블리가 모두 들어갔고 `shop.yaml`과 `rapid-buy.yaml`이 통과, 버그 규칙 둘은 Mono 빌드와 같은 값으로 실패했다(`gift.requests: expected 1, got 5`, `popups: expected 0, got -1`). 4단계의 규칙 6개도 같은 결과였다: 통과, 예외, 크래시(`crash`, 7.9초, 로그 저장, 재실행), 프리징(`freeze`, 로그 저장, 재실행), 그 뒤의 규칙 통과, 다시 돌릴 때 새 게임에서 시작. 예외의 스택에는 함수 이름만 있고 파일과 줄 번호는 없다. 크래시 로그의 스택에는 `GameAssembly.dll` 쪽 함수 이름이 IL2CPP가 만든 C++ 이름으로 남는다(빌드한 PC에서 돌린 경우)
- 대기의 기본 제한 시간: 10초. 프로토콜의 `timeoutMs`는 필수로 두고, 적지 않았을 때 러너와 Python 클라이언트가 이 값을 넣는다
- 결정성에서 도구가 직접 처리할 항목: 누르기 전 자동 대기, Unity 기본 랜덤(`UnityEngine.Random`) 시드 고정
  - 넣지 않기로 한 것: 움직임이 멈출 때까지 대기, 시간 배율 제어
  - 자동 대기는 `tap`의 `timeoutMs`로, 시드 고정은 `seed` 명령으로 넣었다

### 2단계: 기록/재생과 YAML 규칙

만들 것

- 입력 기록: 터치를 받은 요소를 조건 검색 표기로 바꿔 순서대로 저장
- YAML 규칙 파일 읽기와 실행 (에디터 내)
- 사전 검증기: 조건에 걸리는 요소가 없거나 여럿인 경우 검출

조각 순서

1. 규칙 파일 문법 정하기 ([규칙 파일 명세](rules.md))
2. 규칙 읽기: YAML을 명령 목록으로 바꾸고 문법 오류를 알림
3. 규칙 실행: 명령을 에이전트에 보내 통과와 실패를 판정 (에디터 내)
4. 사전 검증기: 규칙의 셀렉터를 현재 화면에 대어 없음과 여럿을 찾음
5. 입력 기록: 사람이 누른 요소를 셀렉터로 바꿔 규칙 파일로 저장

이 단계에서 정한 것 (상세는 [규칙 파일 명세](rules.md))

- 명령 이름과 구조는 Maestro를 따른다. v0 명령은 `tapOn`, `assertVisible`, `assertNotVisible`, `assertValue`, `seed`
- 글자는 정확히 일치로 본다. 모르는 명령과 머리말 필드는 실행 전에 오류로 알린다
- 기록할 때 요소를 적는 순서: 고유 ID, 이름, 글자. 하나로 정해지지 않으면 범위(`within`), 그다음 순서(`index`)를 덧붙인다
- YAML은 라이브러리 없이 직접 읽는다. 규칙 파일 명세에 나온 모양(한 줄짜리 `{ }`)만 읽고, 여러 줄로 들여 쓴 중첩 같은 나머지 문법은 오류로 알린다
- 규칙을 읽는 쪽이 명령을 프로토콜 요청(`cmd`, `args`)으로 미리 바꿔 둔다. 실행하는 쪽은 보내고 판정만 한다
- 규칙을 실행하는 쪽은 "명령 하나를 보내고 응답을 받는 길"만 넘겨받는다. 에디터에서는 프로세스 안의 에이전트, 3단계의 러너에서는 소켓이 그 길이다

- 사전 검증기는 지금 화면 하나만 본다. 요소는 `find`의 `resolves`로, 게임 값은 `get`으로 확인한다
- 입력 기록은 탭만 다룬다. UI 입력 모듈의 누르기 입력을 함께 듣고, 누른 순간의 화면에서 셀렉터를 정한다
- 에디터 창(`qaplay > Rules`) 하나에 기록, 저장, 사전 검증, 실행을 둔다

검증

- PlayMode 테스트가 샘플 화면에서 터치를 기록해 YAML로 만들고, 640x480에서 기록한 것을 540x960에서 재생해 통과한다
- 에디터 창은 사람이 직접 눌러 확인한다(자동 테스트 없음)
- 씬이 바뀌어도 기록이 이어진다. 2026-11-26에 진단용 테스트로 쟀다(배치와 창 모드가 같았다): 기록 중에 씬을 세 번 바꾸고(매번 EventSystem과 입력 모듈이 새로 생긴다) 터치와 마우스로 누른 6번이 모두 기록됐고, 제보에 붙는 조작 이력에도 6줄이 남았다

다음 단계로 넘긴 것

- 탭 이외의 조작(글자 입력, 스크롤, 끌기, 뒤로 가기)의 기록과 재생. 에이전트 명령부터 필요하다
- 씬과 프리팹의 정적 검사(요구사항 9번 [보완])
- 여러 화면을 넘겨 가며 하는 사전 검증

### 3단계: 소켓, 러너, Python 클라이언트

만들 것

- 에이전트 TCP 서버: 길이 접두어 + JSON, 생존 신호(프레임 번호)
- 러너 CLI: 기기 목록, adb forward, 연결, 규칙 파일 실행, 종료 코드, JUnit XML
- Python 클라이언트: `find`, `tap`, `wait`, `get`을 감싼 얇은 라이브러리

조각 순서

1. 에이전트 TCP 서버 (`AgentServer`)
2. 러너 CLI: 접속, 규칙 실행, 종료 코드, JUnit XML (`qaplay run`, `qaplay check`)
3. 재시도와 불안정 판정
4. 러너의 중계와 Python 클라이언트 (`qaplay serve`, `python/qaplay`)
5. Android 기기 목록과 포트 연결 (`qaplay devices`, `--device`)

이 단계에서 정한 것

- 러너와 Python 스크립트의 연결: Python도 러너의 localhost 포트(기본 27276)에 게임과 같은 프로토콜로 접속하고, 러너가 게임으로 중계한다. 프로토콜은 하나로 유지된다
  - 지금의 중계는 바이트를 그대로 옮긴다. 러너가 메시지를 들여다봐야 하는 4단계(크래시 복구)에서 프레임 단위로 바꾼다
- 재시도 기본값: 1번. 다시 돌려 통과하면 불안정(flaky)이고 종료 코드는 성공이다. `--retries N`으로 바꾼다
- 에이전트는 게임이 시작되면 `127.0.0.1:27275`에서 자동으로 기다린다(에디터의 Play와 QA 빌드). 포트는 실행 인자 `-qaplay-port`나 환경 변수 `QAPLAY_PORT`로 바꾼다
- 러너의 종료 코드: 0 모두 통과(불안정 포함), 1 실패가 있음, 2 사용법이 틀렸거나 게임에 닿지 못함
- 러너는 .NET 10으로 만든다. 규칙을 읽고 실행하고 검증하는 코드는 Unity 패키지의 파일을 그대로 가져다 쓴다(두 벌을 만들지 않는다)
- 러너가 게임 없이 확인할 수 있는 로직은 `qaplay selftest`로 검사하고, 게임을 거치는 전체 경로는 PlayMode 테스트(`RunnerTests`)가 러너와 Python을 실제 프로세스로 띄워 확인한다

검증

- PlayMode 테스트가 러너(`qaplay.exe`)와 Python 스크립트를 실제 프로세스로 띄워, 소켓을 거쳐 샘플 화면을 다루게 한다: 통과, 실패, 불안정, 폴더 실행, 사전 검증, 연결 실패, Python 중계
- Windows QA 빌드를 띄워 같은 명령을 돌렸다: `qaplay run`(통과), `qaplay check`, `qaplay serve -- python`(통과), 실패하는 규칙(종료 코드 1). 창에 포커스가 없는 상태에서 가상 터치가 들어갔다
- Android는 2026-11-26에 에뮬레이터(x86_64, Android 17, 1080x2400)와 IL2CPP QA 빌드로 확인했다. 실제 기기는 아직이다(미실측 목록)
  - `qaplay devices`에 `emulator-5554  device  sdk_gphone64_x86_64`, `qaplay run shop.yaml --device`는 `PASS (1.1s)`, `qaplay serve --device -- python shop.py`는 `ok: gold 1100 -> 800 on Android`
  - 인터넷 권한은 Unity가 자동으로 넣었다(`android.permission.INTERNET: granted=true`)
  - 처음에는 러너가 붙지 못했다. IL2CPP 빌드에서 에이전트가 빠져 있었기 때문이다(1단계에 적은 스트리핑 문제). 고친 뒤 통과했다
  - 전체 화면 앱을 처음 띄울 때 뜨는 시스템 안내(Viewing full screen)가 닫히기 전에는 게임이 멈춰 있어 러너가 붙지 못한다(`the game did not answer on port 27275 within 60 s`). 안내를 미리 꺼 두면(`settings put secure immersive_mode_confirmations confirmed`) 통과한다. 러너가 대신 처리할지는 7단계의 OS 다이얼로그 처리에서 정한다

다음 단계로 넘긴 것

- 다시 돌리기 전에 게임을 처음 상태로 되돌리기(앱 재시작, 상태 초기화). 지금은 앞 시도가 남긴 상태에서 이어서 돈다
- 생존 신호로 프리징을 판정하기. 에이전트는 신호를 보내고, 러너는 아직 읽고 버린다
- Wi-Fi 접속과 토큰 검사. 지금은 그 기기 안에서 오는 접속만 받는다
- 사람이 읽는 상세 리포트. 지금은 콘솔 출력과 JUnit XML뿐이다

### 4단계: 크래시 감지와 복구

조각 순서

1. 예외 이벤트(`exception`)와 샘플의 문제 버튼 3개(예외, 크래시, 프리징)
2. 러너의 판정: 예외, 크래시(연결 끊김), 프리징(프레임 번호 멈춤)
3. 러너가 게임을 띄우고 다시 띄우기(`--app`, `--package`), 게임 로그 수집(`--artifacts`)
4. Windows QA 빌드로 전체 검증

이 단계에서 정한 것

- 예외, 크래시, 프리징이 난 규칙은 확인 명령이 모두 통과했더라도 실패이고, 다시 돌리지 않는다. 가끔만 나더라도 버그이므로 재시도로 덮지 않는다
- 프리징 기준은 10초. 생존 신호의 프레임 번호가 그만큼 그대로이면 프리징이다. `--freeze-seconds`로 바꾼다
- 명령의 제한 시간이 지나고도 10초 더 응답이 없으면, 프레임이 돌고 있더라도 프리징으로 본다(요구사항의 "응답 타임아웃")
- 크래시와 프리징의 구분: 죽는 중인 게임은 크래시 기록을 쓰는 동안 연결이 끊기지 않아 프리징처럼 보인다. 러너가 띄운 게임이면 게임의 로그에 남은 크래시 표시(`Crash!!!` 등)로 구분한다
- 복구는 러너가 게임을 직접 띄운 경우에만 한다. 이미 떠 있는 게임이나 에디터에 붙은 경우에는 다시 띄울 수 없어 남은 규칙이 `not_connected`로 실패한다
- 러너가 띄운 게임이면 다시 돌릴 때도 게임을 새로 띄운다. 3단계에서 넘긴 "다시 돌리기 전에 처음 상태로"가 이것으로 해결된다
- IL2CPP 심볼리케이션은 기기 검증이 가능할 때로 미룬다. 지금은 게임이 남긴 로그와 스택을 원문 그대로 저장한다

검증

- `qaplay selftest`: 가짜 게임으로 예외, 크래시, 프리징, "오래 걸리지만 프레임은 도는 응답"을 구분하는지 검사한다
- PlayMode 테스트: 예외 이벤트가 소켓으로 오는지, 예외가 난 규칙이 실패하고 다시 돌지 않는지
- Windows QA 빌드를 러너가 직접 띄워 규칙 6개를 돌렸다: 통과, 예외, 크래시(종료 코드 -1073741819, 로그 저장, 재실행), 프리징(로그 저장, 재실행), 그 뒤의 규칙 통과, 다시 돌릴 때 새 게임에서 시작
- Python 스크립트도 같은 게임으로 돌렸다: 정상 스크립트는 종료 코드 0, 크래시를 내는 스크립트는 종료 코드 1과 로그 저장
- 2026-11-26에 Android 에뮬레이터에서 같은 규칙 6개를 `--device --package`로 돌렸다: 통과, 예외, 크래시(`crash`, 4.3초, logcat 저장, 재실행), 프리징(`freeze`, logcat 저장, 재실행), 그 뒤의 규칙 통과, 다시 돌릴 때 새 앱에서 시작. 크래시의 logcat에는 `Fatal signal 11 (SIGSEGV)`가 남았고, IL2CPP 스택은 주소와 BuildId뿐이라 함수 이름을 알 수 없다(심볼리케이션은 여전히 미뤄 둔다). 프리징의 logcat에는 10초 안에 남는 표시가 없었다
  - 이때 고친 것: 이미 떠 있는 앱은 `--package`로 띄워도 앞으로 나오기만 해서 앞 실행의 상태가 남았다(골드 `300`). 띄우기 전에 앱을 먼저 끝내게 했다
- 같은 날 러너가 띄우지 않은 게임의 크래시를 쟀다. 손으로 띄운 Windows 빌드에서 크래시 규칙을 11번 돌려 10번은 `crash`(4.8초에서 7.6초), 1번은 `freeze`(13.4초, 맨 처음 실행)였다. 죽는 게임이 크래시 기록을 쓰는 시간이 프리징 기준 10초를 넘으면 `freeze`로 나온다. 에디터가 크래시하는 경우는 재지 않았다
- 같은 날 로딩이 길 때의 프리징 기준을 쟀다. 실제 게임이 아니라 버튼이 메인 스레드를 막는 흉내다: 한 번에 5초와 9초는 통과, 11초와 15초는 `freeze: the game stopped at frame N for 10000 ms`, 3초씩 8번(합쳐서 24초)은 통과, `--freeze-seconds 30`이면 15초도 통과. 한 번에 10초 넘게 화면을 막는 로딩이 있는 게임은 기준을 늘려야 한다

다음 단계로 넘긴 것

- Python 스크립트 쪽의 예외와 프리징 판정. 중계가 아직 바이트를 그대로 옮기므로, 스크립트는 크래시만 알 수 있다(연결 끊김). 프레임 단위 중계는 필요해질 때 만든다
- 크래시 건을 버그 제보 형식으로 자동 등록(5단계)
- 크래시 직전 조작 이력을 러너 쪽에 실시간으로 남기기(5단계의 조작 이력과 함께)
- OOM 강제 종료의 추정(7단계의 메모리 기록과 함께)
- Android의 tombstone 수집. 지금은 logcat만 남긴다

### 5단계: 버그 제보와 회귀 편입

조각 순서

1. 게임 안의 상시 조작 이력과 제보 저장 (`BugReporter`, 명령 `report`, `reports`, `reportGet`, `reportDelete`)
2. PC로 가져오기와 버그 관리 명령 (`qaplay bugs pull / report / list / show / set / delete`)
3. 회귀 규칙 만들기와 해결 확인 (`qaplay bugs promote / verify`)
4. 예외, 크래시, 프리징의 자동 등록과 같은 버그 묶기

이 단계에서 정한 것 (상세는 [버그 리포트](bugs.md))

- 범위: 제보, 가져오기, 관리 명령, 회귀 규칙, 자동 등록까지 만든다. 확인 대기 목록, 합치기와 나누기, 수정 이력, 재현율은 뒤로 미룬다
- 게임에서 건 제보는 제목을 받지 않고 바로 저장한다. 제목과 설명은 PC로 가져온 뒤에 적는다. 플레이 흐름이 끊기지 않고, 입력 창이 게임 UI와 섞이지 않는다
- 제보를 거는 방법: 키보드 F12, 세 손가락으로 1초 누르기, `qaplay bugs report`, Python의 `game.report()`
- 조작 이력은 Play 동안 늘 쌓는다(최근 5분, 최대 200개). 2단계의 입력 기록기가 늘 듣게 바꿨다
- 버그를 "해결됨"으로 바꾸는 것만으로는 아무것도 실행하지 않는다. `qaplay bugs verify`가 회귀 규칙을 돌려 통과하면 `verified`, 실패하면 `open`으로 바꾼다
- 같은 버그의 기준: 예외는 종류와 맨 위 호출 지점, 크래시와 프리징은 규칙 파일. 크래시의 네이티브 스택은 심볼리케이션과 함께 본다
- 리포트 삭제 시 연동 이슈를 어떻게 할지는 연동을 만드는 9단계에서 정한다. 지금의 삭제는 PC의 폴더만 지운다

검증

- PlayMode 테스트: 제보 명령 4개, F12, 세 손가락 누르기, 그리고 러너를 실제 프로세스로 띄워 "제보 → 가져오기 → 제목 적기 → 회귀 규칙 → 해결 확인 → 다시 실패하면 회귀로 다시 열림"과 "예외의 자동 등록과 묶기"
- `qaplay selftest`: 저장소의 번호 매기기, 같은 버그 가리기, 다시 열기
- Windows QA 빌드: 화면이 담긴 제보를 가져오고, 크래시가 로그와 함께 자동 등록되는지
- Android 에뮬레이터(2026-11-26): 에뮬레이터의 터치 장치에 세 손가락 누르기를 넣었다(사람 손이 아니라 기기 안의 입력 장치에 직접 쓴 것이다). 0.5초는 제보가 생기지 않았고 1.5초는 생겼다. `qaplay bugs pull --device`로 가져오니 화면(1080x2400, 250,348바이트), 직전 조작 세 줄, 기기 정보(`Android OS 17 / API-37`)가 들어 있었고 기기의 폴더는 비워졌다. 1초가 안 된 세 손가락 누르기는 조작 이력에 `# not recorded` 주석 한 줄로 남는다

### 6단계: 입력 스트레스

조각 순서

1. 연타와 동시 클릭: 프로토콜 `tap`의 `count`와 `intervalMs`, 명령 `tapTogether`, 규칙의 `repeat`, `delay`, `tapTogether`, 버그를 심은 샘플 버튼 둘
2. AI가 규칙을 쓸 때 필요한 조회 명령과 기계용 출력: `qaplay dump`, `qaplay values`, `--json`
3. AI 도구용 안내 문서 (패키지의 `Documentation~/ai-guide.md`)

이 단계에서 정한 것 (상세는 [규칙 파일 명세](rules.md) 4절, [프로토콜 명세](../protocol/README.md)의 `tap`과 `tapTogether`)

- 검증 대상: 규칙에 적은 버튼만 본다. 화면의 버튼을 스스로 찾아 누르는 것은 11단계(자동 탐색)에서 다룬다. 기대 결과가 없는 버튼은 판정할 수 없고, 누르면 화면이 바뀌어 순회 순서와 되돌리기를 정해야 하기 때문이다
- 판정: 연타와 동시 클릭은 누르기만 한다. 기대 결과는 원래 있던 `assertValue`, `assertVisible`로 적는다
- 연타는 누를 자리를 처음에 한 번만 정하고, 버튼이 꺼지거나 가려져도 같은 자리를 계속 누른다. 빠르기는 두 프레임에 한 번이다
- 동시 클릭은 요소가 모두 누를 수 있는 프레임에 한꺼번에 누르고 다음 프레임에 함께 뗀다
- 규칙 문법: `repeat`와 `delay`는 Maestro의 이름을 그대로 쓴다. 동시 클릭은 Maestro에 없어서 `tapTogether`를 새로 두고, 그 인자를 위해 한 줄짜리 목록 `[ ]`을 읽게 했다
- 규칙의 생성, 수정, 삭제 명령은 만들지 않는다. 규칙은 저장소의 파일이고 AI 도구는 파일을 직접 고친다. 러너는 그때 필요한 조회(`dump`, `values`), 검사(`check`), 시험 실행(`run`)과 JSON 출력을 준다
- `--json`을 붙이면 표준 출력에는 결과 JSON 하나만 나오고, 사람이 읽는 줄은 표준 오류로 간다

만들면서 알게 된 것

- 먼저 처리된 클릭이 팝업을 바로 끄거나(`SetActive(false)`) 바로 없애면(`Destroy`), uGUI는 같은 프레임의 나머지 클릭을 전달하지 않는다(측정: 두 번째 버튼에는 뗌 이벤트도 가지 않았다). 동시 클릭 버그는 닫히는 연출처럼 팝업이 잠시 남아 있을 때 난다. 샘플의 판매 팝업은 0.2초 뒤에 없어지게 해서 버그를 심었다

검증

- PlayMode 테스트: 연타가 누른 만큼만 처리되는지(5번, 30번, 간격을 둔 3번, 마우스가 움직이는 중의 10번), 버그를 심은 샘플 버튼 둘을 규칙이 잡아내는지, 하나씩 누르면 같은 규칙이 통과하는지, 동시 클릭이 하나라도 누를 수 없으면 아무것도 누르지 않는지
- 러너를 실제 프로세스로 띄워: 샘플 규칙 셋의 통과와 실패, `dump`와 `values`의 출력, `--json`의 표준 출력이 JSON 하나인지
- `qaplay selftest`: 값이 없는 옵션 `--json`
- Android 에뮬레이터(2026-11-26, 실제 터치 장치와 가상 터치스크린이 함께 있다): `rapid-buy.yaml`은 통과, `rapid-gift.yaml`은 `gift.requests: expected 1, got 5`, `together-sell.yaml`은 `popups: expected 0, got -1`로 에디터와 같았다

미룬 것

- 한 프레임 안에 닫히는 틈을 잡는 연타(뗌과 다음 누름을 같은 프레임에 넣는 방식)
- `qaplay bugs`의 JSON 출력
- 요소마다 추천 셀렉터를 알려 주는 것. 지금은 `dump`를 보고 규칙을 쓰는 쪽이 고른다

### 7단계: 메모리, 기기 지표, 플러그인 Mock

조각 순서

1. 메모리 읽기와 예산: 프로토콜 `memory`, 규칙의 `assertMemory`, `qaplay memory`
2. 누수 감지: 규칙을 되풀이하며 메모리를 기록하고 증가 추세로 판정, 누수를 심은 샘플 팝업
3. 프레임 시간 지표와 예산(에이전트가 잰다)
4. OS에서 얻는 지표(CPU, 발열, 배터리, 프로세스 메모리)와 플랫폼별 지원 표(러너가 잰다)
5. OS 다이얼로그가 뜨지 않게 미리 처리(러너, Android)
6. 플러그인 호출 검증과 Mock: 확장 지점, 응답 시나리오, 샘플의 가짜 결제, Mock이 출시 빌드에 들어가지 않는지

이 단계에서 정한 것

- 범위: 메모리, 기기 지표, 플러그인 Mock을 모두 이 단계에서 만든다. 메모리부터 한다
- 기본 Mock: SDK별 기본 Mock(Unity IAP 등)은 만들지 않는다. 프로젝트가 SDK 호출을 인터페이스로 감싸고 테스트가 응답 시나리오를 고르는 확장 지점과, 샘플 상점의 가짜 결제 하나만 제공한다. SDK용 Mock은 패키지 버전에 묶이고 샘플 프로젝트에 그 패키지를 넣어야 한다
- OS 다이얼로그: 뜬 것을 찾아 누르지 않고, 뜨지 않게 미리 처리한다. 러너가 Android 앱을 띄우기 전에 권한을 미리 주고 전체 화면 안내를 꺼 둔다. 예상하지 못한 다이얼로그는 지금처럼 러너가 붙지 못하는 실패로 드러난다
- 실패 시 메모리 스냅샷: 찍지 않는다. 잰 숫자의 이력만 남긴다. 스냅샷은 Development 빌드에서만 되고, 찍는 동안 게임이 멈추며 파일이 크다
- 플랫폼별 지표 지원 표와 Development 빌드 전용 지표의 구분은 미리 정하지 않고, 조각을 만들면서 잰 결과로 채운다
- 메모리 읽기(조각 1, 상세는 [프로토콜 명세](../protocol/README.md)의 `memory`, [규칙 파일 명세](rules.md) 4절)
  - 세 계층을 한 번에 읽는다: `managed`(C# 힙), `native`(Unity 네이티브), `process`(OS가 본 프로세스 전체)
  - 재기 전에 쓰레기 수집을 한 번 한다. 쓰레기는 세지 않아야 잴 때마다 같은 기준이 된다. 쓰지 않는 에셋은 내리지 않는다. 없애지 않고 버린 텍스처 같은 누수가 숫자에 남아야 하기 때문이다
  - 규칙의 예산은 `assertMemory: { 계층: MB }`다. 단위는 MB 하나이고, 단위를 붙여 쓰면(`64MB`) 오류다. 예산을 넘으면 `over_budget`
  - 읽을 수 없는 계층에 예산을 적으면 실패다. 확인하지 못한 것을 통과로 두지 않는다
  - 미룬 것: 명령 전후와 일정 주기의 자동 샘플링(조각 2에서 반복마다 재는 것으로 시작한다), Android의 PSS(조각 4에서 러너가 OS에서 읽는다)
- 누수 감지(조각 2, 상세는 [규칙 파일 명세](rules.md) 4절의 누수 검사)
  - 문법: `- leakCheck: 20` 줄 아래의 명령을 파일 끝까지 한 묶음으로 되풀이한다. 그 줄 위는 준비로 한 번만 실행한다. Maestro처럼 묶음을 들여 쓰는 `repeat`는 한 줄 문법에 맞지 않아 쓰지 않았다
  - 판정: 되풀이마다 `memory`로 재고, 잰 값의 뒤쪽 절반에 직선을 그어(최소제곱) 되풀이 한 번에 는 양을 본다. 앞쪽 절반은 풀과 캐시가 차는 구간으로 보고 버린다. 처음과 끝만 빼는 것보다 한 번 튄 값에 덜 흔들린다
  - 기본 허용치는 되풀이 한 번에 0.05MB다. 누수가 없는 화면에서 잰 흔들림(가장 큰 것이 0.003MB)의 열 배 이상이고, 규칙의 `allow`로 바꿀 수 있다
  - 판정하는 계층은 `managed`와 `native`다. `process`는 기록만 한다(가만히 있어도 OS가 올리고 내린다). 그래서 네이티브 플러그인만 새는 누수는 잡지 못한다
  - 잰 값은 통과했어도 `--artifacts` 폴더에 `규칙이름.memory.csv`로 남긴다. 실패 시 스냅샷 대신 남기는 숫자 이력이 이것이다
  - 실패 코드는 `leak`이다. 예외, 크래시, 프리징과 달리 다시 돌리기 대상이다(잰 값이 흔들릴 수 있다)
  - 샘플에 심은 누수: 보상 팝업은 열 때마다 1MB 텍스처를 만들고, 닫을 때 팝업만 없애고 텍스처는 없애지 않는다
- 프레임 시간(조각 3, 상세는 [프로토콜 명세](../protocol/README.md)의 `frames`, [규칙 파일 명세](rules.md) 4절의 프레임 시간 예산)
  - 지표: 평균(`average`), 느린 쪽 1%의 경계(`p99`, 99번째 백분위), 끊김 횟수(`hitches`). 요구사항의 "하위 1%"를 프레임 시간의 99번째 백분위로 정했다
  - 끊김의 기준은 50ms보다 오래 걸린 프레임이고, 규칙의 `hitchOver`로 바꾼다. 30fps 게임은 프레임 하나가 33ms라 조금만 밀려도 넘으므로 기준을 올려 쓴다
  - 재는 구간: `frames` 요청마다 그 앞의 요청부터의 프레임을 요약해 주고 새로 잰다. 규칙은 시작할 때 한 번 보내 두어서, `assertFrameTime`은 규칙의 시작(또는 앞의 `assertFrameTime`)부터를 본다. 시작과 끝을 표시하는 명령을 따로 두지 않았다
  - 켜고 끄기: 따로 옵션을 두지 않았다. 처음 `frames`를 받을 때부터 재므로, 쓰지 않는 게임에서는 프레임마다 하는 일이 없다. 재는 동안에는 프레임마다 시각을 한 번 읽어 배열에 적는다(최근 36000프레임, 한 번만 잡는다)
  - 예산 초과의 실패 코드는 메모리와 같은 `over_budget`이다
  - 샘플에 심은 끊김: 정렬 버튼은 메인 스레드를 0.15초 막는다
- OS에서 얻는 지표(조각 4, 상세는 [규칙 파일 명세](rules.md) 4절의 기기 지표 예산)
  - 러너가 읽는다. Android는 adb 셸 한 번으로 모은다: `/proc/<pid>/stat`과 `/proc/uptime`(CPU), `dumpsys thermalservice`(발열 단계), `dumpsys battery`(남은 양과 온도), `dumpsys meminfo -s`(PSS). PC 빌드는 러너가 띄운 프로세스의 CPU 시간만 읽는다
  - 에이전트의 명령이 아니다. 규칙의 `assertDevice`는 `device` 요청이 되고, 러너가 가로채 답한다. 그래서 러너 없이 에디터 창에서 돌리면 `unknown_command`다. 프로토콜 명세에는 넣지 않았다
  - CPU 사용률은 코어 하나 기준(100 = 코어 하나를 다 씀)이고, 구간은 프레임 시간처럼 규칙의 시작(또는 앞의 `assertDevice`)부터다. CPU 시간과 시각을 모두 기기에서 읽어 adb가 오가는 시간이 섞이지 않게 했다
  - 1초보다 짧은 구간의 CPU는 재지 못한 것으로 둔다. 명령 하나짜리 규칙에서 `cpu 0 %`가 나와 예산을 그냥 통과하는 것을 보고 넣었다(OS가 CPU 시간을 10~16ms 단위로 센다)
  - Android의 패키지 이름은 `--package`가 없으면 게임이 `hello`로 알려 준 `app.id`를 쓴다
  - 배터리 소모는 판정하지 않는다. 남은 양(%)을 읽어 보여 주기만 한다. adb를 USB로 쓰면 충전 중이라 줄지 않는다. 배터리 쪽 예산은 온도뿐이다
  - 요구사항에 적힌 "OS 기준 프로세스 전체 메모리(Android PSS)"는 이 조각의 `pss`다. 조각 1의 `process`는 RSS였다

만들면서 알게 된 것

- 빌드에서는 `Time.unscaledDeltaTime`으로 끊김을 잴 수 없다. 화면 주사율에 맞춰 다듬어진 값이 나온다. Windows 빌드에서 0.15초 멈춘 프레임이 Mono는 50ms, IL2CPP는 16.67ms로 나왔고, 가만히 둔 화면은 모든 프레임이 정확히 16.67ms였다. 에디터에서는 그대로 나와서 PlayMode 테스트만으로는 드러나지 않았다. 프레임 사이의 실제 시각(`Time.realtimeSinceStartupAsDouble`)을 직접 빼도록 고친 뒤 161~167ms로 잡혔다

플랫폼별 지표 지원 표 (잰 것만 적는다. 모두 Development 빌드가 아닌 빌드에서 쟀고, 지금까지 Development 빌드에서만 되는 지표는 없다. iOS는 10단계에서 채운다)

검증

- 조각 1 (2026-11-28)
  - PlayMode 테스트(배치 201개 통과, 창 모드는 메모리 테스트 5개만): 세 값이 나오는지, 쥐고 있는 32MB는 `managed`에 세고 버린 64MB는 세지 않는지, 없애지 않고 버린 16MB 텍스처가 `native`에 남고 없애면 돌아오는지, 예산 안은 통과하고 넘으면 `over_budget`인지, 러너의 `qaplay memory`와 예산 규칙
  - Windows QA 빌드(Development 빌드 아님)의 샘플 화면: Mono는 `managed` 2.3MB, `native` 57.6MB, `process` 402.8MB. IL2CPP는 2.2MB, 73.9MB, 389.7MB. `process`는 같은 순간 OS가 본 작업 집합과 같았다(Mono 403.1MB, IL2CPP 390.4MB). 커밋 크기(Private, 688MB)와는 다르다
  - Android 에뮬레이터(IL2CPP, x86_64): 4.2MB, 45.0MB, 280.5MB. `process`는 RSS(287,380kB = 280.6MB)와 같고 PSS(153,939kB)보다 크다
  - 가만히 둔 화면에서 연달아 5번 쟀을 때: `managed`와 `native`는 0.1MB 안에서 같았다. `process`는 잴 때마다 0.3MB쯤 올랐고, Windows에서는 한 번 20MB 가까이 내려가기도 했다(작업 집합 정리). 누수 판정(조각 2)은 `process`의 이 흔들림을 감안해야 한다
  - 세 플랫폼 모두 넉넉한 예산 규칙은 통과, 아주 작은 예산 규칙은 `over_budget`으로 실패(종료 코드 1)
- 조각 2 (2026-11-28)
  - PlayMode 테스트(배치 215개 통과, 창 모드는 메모리와 러너 쪽 12개만): 샘플의 누수 규칙이 `leak`으로 실패하는지, 누수가 없는 팝업은 통과하는지, 1MB씩 쥐는 C# 쪽 누수를 잡는지, `leakCheck` 위의 명령은 한 번만 실행하는지, 되풀이 중의 실패가 몇 번째인지 알리는지, 러너가 기록 파일을 남기는지
  - `qaplay selftest`: 추세 계산이 계속 느는 것만 잡고, 앞쪽에서만 늘다 멈춘 것과 한 번 튄 값에는 넘어가지 않는지
  - 샘플의 누수 규칙(`BuggyRules/leak-reward.yaml`, 20번): 에디터 1.03MB, Windows Mono 1.001MB, Windows IL2CPP 1.001MB, Android 에뮬레이터 1.001MB씩 `native`가 늘어 모두 `leak`으로 실패했다(예: `native grew 1.001 MB per repeat (58.7 MB -> 77.7 MB over 20 repeats, allowed 0.05 MB per repeat)`). 이때 `process`도 되풀이마다 1.3MB쯤 늘었다
  - 누수가 없는 동작 넷(안내 팝업 20번과 100번, 판매 팝업을 만들었다 없애기 20번, 구매 알림 20번)은 세 빌드 모두 통과했고, 증가 추세는 -0.003 ~ +0.001MB였다
  - 미실측: 네이티브 플러그인만 새는 누수, 실제 게임 크기의 화면에서의 흔들림(샘플 화면으로만 쟀다)
- 조각 3 (2026-11-28)
  - PlayMode 테스트(배치 229개 통과. 창 모드는 프레임, 메모리, 기록 쪽 25개 중 24개 통과와 원래 건너뛰는 1개. 실제 시각으로 고친 뒤에는 프레임 쪽 8개만 배치로 다시 돌렸다): 요청 사이의 프레임만 요약하는지, 120ms 멈춘 프레임을 끊김으로 세고 기준을 올리면 세지 않는지, 샘플의 끊김 규칙이 `over_budget`으로 실패하는지, 규칙이 `hitchOver`를 쓰고 확인할 때마다 새로 재는지, `qaplay frames`
  - 샘플의 끊김 규칙(`BuggyRules/hitch-sort.yaml`): Windows Mono `longest 161.1 ms`, Windows IL2CPP `166.7 ms`, Android 에뮬레이터 `182.2 ms`로 모두 실패했다. 기준을 500ms로 올린 규칙은 세 곳 모두 통과했다
  - 가만히 둔 화면 5초: Windows 빌드는 둘 다 `average 16.67 ms, p99 16.8 ms`(60fps), 에뮬레이터는 `average 33.34 ms, p99 35.9 ms`(30fps)이고 끊김은 없었다
  - 끊김이 없어야 하는 동작(팝업 열고 닫기, 구매와 알림, 판매 팝업): Windows 빌드는 둘 다 통과(`longest 21.4 ms`, `17.1 ms`). 에뮬레이터에서는 55.8ms 프레임 하나가 50ms 기준에 걸려 실패했다. 30fps에서는 기준을 올려 써야 한다는 것을 이 결과로 문서에 적었다
  - 미실측: 실제 Android 기기, 재는 것 자체가 프레임 시간에 주는 영향
- 조각 4 (2026-11-28)
  - PlayMode 테스트(배치 237개 통과, 창 모드는 돌리지 않았다): `assertDevice`의 문법, 에디터 안에서는 `unknown_command`로 실패하는지, 에디터에 붙기만 한 러너는 `not available`로 알리고 예산을 통과시키지 않는지
  - `qaplay selftest`: 에뮬레이터에서 받은 셸 출력으로 CPU 시간, 발열 단계, 배터리, PSS를 읽는지, 앱이 떠 있지 않을 때 빈 값으로 두는지
  - Android 에뮬레이터, 가만히 둔 화면 10초: `cpu 14.5 %, pss 160.6 MB, thermal 0, battery 100 %, battery temperature 25 C`. 같은 때 `top`은 CPU를 16.0으로 보였고, `dumpsys meminfo`의 `TOTAL PSS`는 152,360~159,000kB대였다
  - Android 에뮬레이터, 규칙(구매 네 번, 3초): 넉넉한 예산은 통과(`cpu 17.5 %, pss 163.2 MB`), 아주 작은 예산은 `over_budget: cpu: 17.5 %, budget 0.01 %; pss: 165.3 MB, budget 1 MB`
  - Windows 빌드(`--app`), 같은 규칙: Mono `cpu 16.7 %`, IL2CPP `cpu 5.4 %`로 통과. `pss`를 적은 규칙은 `pss: not available here`로 실패
