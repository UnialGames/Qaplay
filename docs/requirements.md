# qaplay: 자동화 QA 프로그램 요구사항 (v0.1)

> 프로젝트 이름: qaplay [확정]. GitHub 저장소, CLI 명령, Python 라이브러리 이름을 통일. Unity 패키지는 com.qaplay.* 형식 [보완]

> 상태 표기: [확정] 방향이 정해짐 / [보완] 내용은 있으나 구체화 필요 / [미정] 결정이 필요함

### 0-1. 범용/오픈 소스 전제에 따른 설계 원칙

- 특정 프로젝트 코드에 의존하지 않음. 프로젝트별 요소는 전부 확장 지점으로 분리 [확정]
  - 확장 지점: 요소 식별, 불변식 등록, 대기 조건, 리포트 출력, 제보 저장소
- 배포 형태: UPM 패키지 (git URL 설치) [보완]
- 코어와 연동 모듈 분리: 코어는 외부 의존성 없음, Google Sheets/Jira 등은 선택 설치 모듈 [보완]
- 설치 후 코드 수정 없이 동작하는 기본값 제공 (기록/재생, 연타 검증, 겹침 검증) [보완]
- 라이선스: MIT [확정]
- 지원 Unity 버전: Unity 6.3 LTS 이상 [확정]
  - 이전 버전(6.0, 2022.3)은 지원하지 않음. 요청이 있으면 추후 검토
- 입력 시스템 지원 범위: 신형(Input System 패키지) 먼저 구현, 구형(Input Manager)은 요청이 있으면 추가 [확정]
  - 구형만 쓰는 프로젝트에 설치하면 "지원하지 않는 입력 방식"임을 명확히 안내 [보완]
  - 입력 주입부를 교체 가능한 구조로 분리해 구형 추가 시 코어 수정이 없도록 함 [보완]
- 문서와 샘플 프로젝트 제공 [보완]

## 2. 외부 테스트 케이스(TC) 연동

- Excel, Google Sheets 등 외부 문서에서 TC 목록 조회 및 동기화 [확정]
- 외부 시트에 등록된 시나리오와 연관된 TC 자동 생성 및 실행 [보완]
  - 역할 분리: 시트와 규칙 파일을 TC 번호로 연결 [확정]
    - 시트: TC 목록, 설명, 기대 결과, 실행 결과. 기획자와 QA가 작성
    - 규칙 파일: 실행 규칙(어떤 요소를 조작해 무엇을 검사). 프로젝트 저장소에 두고 Git으로 관리. AI와 프로그래머가 작성
    - 같은 내용을 양쪽에 두고 동기화하지 않음
  - 작성과 실행 흐름 [확정]
    1. 사람이 시트에 TC 한 줄 작성 (무엇을 확인할지)
    2. 사람이 AI에게 해당 TC의 규칙 작성 요청
    3. AI가 CLI로 시트의 TC 읽기
    4. AI가 CLI로 화면 요소와 게임 값 조회
    5. AI가 규칙 파일 생성
    6. AI가 검증기와 시험 실행으로 확인
    7. 사람이 규칙 파일 검토 후 Git 반영
    8. 러너가 규칙 파일 읽기
    9. 러너가 테스트 실행
    10. 러너가 시트의 해당 TC 줄에 결과 기록
  - 시트의 기대 결과가 바뀐 TC는 러너가 "규칙 갱신 필요"로 표시 [보완]
  - 시트 구성: TC 탭 + 요약 탭 [확정]
    - TC 탭: TC 한 줄에 최신 결과만 표시. 개별 실행 이력은 쌓지 않음
    - 요약 탭: 빌드마다 한 줄 추가 (빌드 버전, 실행 일시, 전체/통과/실패/불안정 수, 통과율)
    - 개별 실행 이력과 증거는 러너가 보관 정책(10번)에 따라 보관, 러너 리포트에서 조회
  - TC 탭 칸 구성 [보완]
    - 사람이 적는 칸: TC 번호, 화면, 사전 조건, 내용(스텝), 기대 결과, 우선순위
    - 도구가 채우는 칸: 규칙 상태(있음/없음/갱신 필요), 최신 결과(통과/실패/불안정/미실행), 최신 실행 정보(빌드, 기기, 일시), 연결된 버그 리포트, 러너 리포트 링크
    - 도구는 자기 칸만 수정하고 사람이 적은 칸은 건드리지 않음 [확정]
    - 칸 이름과 위치는 설정으로 지정 가능. 팀이 쓰던 시트 양식을 그대로 사용 [확정]
  - 버그 리포트는 시트에 쌓지 않음. 로컬 파일과 Jira/Notion에 두고 TC 탭에는 링크만 표시 [확정]
  - 규칙 파일 형식: YAML [확정]
    - 명령을 한 줄씩 나열하는 구조. Maestro의 명령 이름과 구조를 따름 [확정]
    - 주석으로 작성 사유를 남길 수 있음
    - 버그 제보의 조작 기록(5번)도 같은 YAML 형식으로 저장해 회귀 테스트 규칙으로 바로 전환 [보완]
    - 복잡한 시나리오(조건, 반복)는 Python 스크립트로 작성 [확정]
    - 명령 목록과 세부 문법: [규칙 파일 명세](rules.md) v0 [확정]
      - 명령: `tapOn`, `assertVisible`, `assertNotVisible`, `assertValue`, `seed`
      - 조작을 기록할 때 요소를 적는 순서: 고유 ID, 이름, 글자. 하나로 정해지지 않으면 범위, 그다음 순서를 덧붙임
- 테스트 실행 결과(성공/실패, 스크린샷, 로그 등) 자동 리포팅 [확정]
  - 리포트 포함 정보: 기기, OS, 빌드 버전, 실행 시간 [보완]
  - 리포트 저장 위치: 시트에는 최신 결과와 빌드별 요약만 기록, 개별 실행 이력과 증거는 러너 리포트에 보관 [확정]
  - 별도 대시보드 제공 여부 [미정]

## 3. 시각 및 UI 실측 검증

- 비동기 리소스 로드 시 이전 이미지가 노출되는 잔상(Ghosting) 현상 감지 [확정]
  - 감지 방식: 로드 요청 후 완료 전에 이전 스프라이트가 보이는 프레임을 컴포넌트 단에서 감지 [보완]
  - 대상 로딩 경로 (Addressables, 웹 이미지 등) [미정]
- 실제 렌더링 화면 기준 UI 요소 간 겹침 및 텍스트 넘침(Overflow) 실측 [확정]
  - 측정 방식: RectTransform 화면 좌표 + TMP overflow 정보 [보완]
  - 의도된 겹침 처리: 자동 제외 후 남은 것만 예외 등록 [확정]
    - 자동 제외 대상: 부모와 자식 관계, 배경 이미지, 터치가 안 되는 장식 요소 [보완]
    - 남은 겹침은 예외 목록에 등록해 이후 검사에서 제외
    - 예외 등록, 조회, 수정, 삭제를 CLI 명령으로 제공. 사람과 AI 모두 사용 [확정]
    - 예외 목록은 규칙 파일과 같이 프로젝트 저장소의 파일로 저장, 사람이 검토 후 Git 반영 [보완]
    - 예외마다 등록 사유를 남김 [보완]
    - AI 판단용 조회 명령: 겹친 두 요소의 정보와 해당 화면 스크린샷 [보완]
    - 자동 제외 규칙의 세부 기준 [미정]
  - 언어 전환, 해상도/세이프에어리어 순회 검증 [보완]

## 4. 입력 스트레스 및 예외 상황 검증

- 동일 버튼 연속 클릭(연타) 시 중복 처리 여부 검증 [확정]
- 서로 다른 버튼(예: 확인, 닫기) 동시 클릭 시 입력 충돌 및 상태 꼬임 검증 [확정]
- 판정 기준: 프로젝트가 테스트 규칙으로 기대 결과를 지정 [확정]
  - 예: "구매 버튼은 몇 번을 눌러도 재화 차감 1회", 서버 요청 1회, 팝업 스택 수 일치
  - 규칙이 없는 버튼은 판정하지 않음. 예외와 크래시는 6번에서 별도로 수집됨
- 테스트 규칙을 AI로 작성 [확정]
  - Claude Code, Codex 같은 AI 코딩 도구가 실행할 수 있는 CLI 명령 제공
  - 규칙의 생성, 수정, 삭제는 파일을 직접 편집해서 함. 규칙은 저장소의 파일이고 AI 도구는 파일을 고칠 수 있으므로, 그것을 위한 명령은 따로 두지 않음 [확정]
  - 사람도 같은 명령과 같은 파일을 씀
  - AI가 규칙을 쓰려면 필요한 조회 명령 [확정]
    - 현재 화면의 요소 목록(UI 계층 덤프) 조회: `qaplay dump`
    - 읽을 수 있는 게임 값(재화 등) 목록 조회: `qaplay values`
    - 규칙 문법 검사, 요소 조건 검증(사전 검증기 연동): `qaplay check`
    - 규칙 시험 실행 후 결과 확인: `qaplay run`
  - 명령 출력은 사람용 텍스트와 기계용 JSON 둘 다 지원: 위 네 명령의 `--json` [확정]
  - AI 도구용 사용 안내 문서를 패키지에 포함: `Documentation~/ai-guide.md` [확정]
  - 규칙 저장 위치: 프로젝트 저장소의 파일 (2번 참고) [확정]
- 검증 대상 버튼 선정 방식: 규칙에 적은 버튼만 (지정 목록). 화면 전체 자동 순회는 자동 탐색(5번)에서 다룸 [확정]

  - 범위 제한: 크래시/예외 발생 지점까지의 랜덤 또는 가이드 탐색

  - 연동 모듈 공통 인터페이스: 등록, 첨부 업로드, 상태 조회 [보완]

    - 닫힌 버그가 재발하면 다시 열고 "회귀"로 표시
    - 발생 횟수와 실행 횟수로 재현율을 자동 계산해 리포트에 기록

      - 규칙 실패: TC 번호 + 실패한 검사 항목 기준
      - 시각 검증 실패: 화면 + 관련 요소 기준
      - 수동 제보: 자동 판별이 어려움. 유사 리포트를 후보로 보여 주고 사람이 선택
    - 잘못 묶인 건을 나누거나 따로 만들어진 건을 합치는 명령 제공 [보완]
    - 연동 대상(Jira 등)에는 댓글이나 필드 갱신으로 반영하고 새 이슈를 만들지 않음 [보완]
  - 이슈 관리 도구 계정 정보(토큰)는 저장소에 넣지 않고 환경 변수 등으로 주입 [보완]
  - 이슈가 "해결됨"이 되면 해당 회귀 테스트 재실행 여부: 상태를 바꾸는 것만으로는 실행하지 않음. 확인 명령(`qaplay bugs verify`)을 따로 두어 통과하면 "확인됨", 실패하면 다시 "열림" [확정]

## 7. Native 및 메모리 측정

- 메모리 측정 [확정]
  - 측정 계층 구분 [보완]

  - 누수 감지: 같은 시나리오(예: 팝업 열고 닫기)를 N회 반복 후 증가 추세로 판정 [보완]
  - 메모리 예산(상한) 설정 후 초과 시 실패 처리 [보완]
  - 실패 시 메모리 스냅샷은 찍지 않음. 잰 숫자의 이력만 남김 [확정]
- Native 관련 범위: 아래 4가지 모두 포함 [확정]
  - Native 크래시 수집 (6번)
  - Native 메모리 측정 (위 항목)
  - Native 플러그인 호출 검증
  - 기기 지표 측정
- Native 플러그인(Android/iOS SDK 연동) 호출 검증 [보완]
  - 호출 성공 여부, 콜백 도착 여부와 응답 시간, 예외 발생 여부
  - 범용 처리 방식: 프로젝트가 검증할 호출을 등록하는 확장 지점 제공 [보완]
  - 결제, 로그인, 광고 흐름의 3구간 구분 [확정]
    - 요청 (버튼 클릭, SDK 호출): 에이전트가 수행
    - 승인 (OS 시스템 UI 조작): 게임 프로세스 밖이라 에이전트 불가
    - 결과 (콜백, 영수증 검증, 재화 지급): 에이전트가 관찰 및 검증
  - 승인 구간 처리: Mock 구조를 기본으로 함 [확정]
    - 성공/실패/취소/지연/중복 콜백 등 응답 시나리오를 테스트에서 지정
    - 전제: 프로젝트가 SDK 호출을 인터페이스로 감싸고 있어야 Mock 교체 가능. 그 연결 방법을 문서와 샘플로 제공 [보완]
    - 자주 쓰는 SDK(Unity IAP 등)용 기본 Mock은 제공하지 않음. 연결 방법과 샘플의 가짜 결제만 제공 [확정]
    - Mock은 QA 빌드에만 포함, Release 빌드 포함 금지를 빌드 검증에 추가 [보완]
  - 실제 SDK 검증(러너가 OS 단에서 탭, 스토어 테스트 계정 사용)은 후순위 확장 [보완]
  - 권한 팝업 등 OS 다이얼로그: 뜨지 않게 러너가 미리 처리(Android에서 권한을 미리 주고 전체 화면 안내를 끔). 뜬 것을 찾아 누르지는 않음 [확정]
- 기기 지표 측정 [보완]
  - 프레임 시간(평균, 하위 1%, 끊김 횟수), CPU 사용률, 발열 상태, 배터리 소모
  - 수집 주체: 게임 내에서 얻는 값(프레임 시간)은 에이전트, OS에서 얻는 값(CPU, 발열, 배터리)은 러너 [보완]
  - 플랫폼별로 얻을 수 있는 지표가 다름. 지원 표는 잰 결과로 [작업 계획](plan.md)의 7단계에 둠(에디터, Windows, Android. iOS는 10단계) [확정]
  - 배터리 소모는 판정하지 않고 남은 양과 온도만 읽음. adb를 USB로 쓰면 충전 중이라 소모를 잴 수 없음 [확정]
  - 지표별 예산(상한) 설정 후 초과 시 실패 처리 [보완]
  - 측정 자체가 성능에 주는 영향 최소화, 측정 켜고 끄기 옵션 [보완]
- 측정 수단 제약: 지금 재는 지표(메모리 세 계층, 프레임 시간, CPU, PSS, 발열 단계, 배터리)는 모두 Development 빌드가 아닌 빌드에서 됨을 확인. Development 빌드 전용 지표는 쓰지 않음(메모리 스냅샷은 찍지 않기로 함) [확정]
- 측정 결과를 2번 리포트에 포함, 빌드 간 추이 비교 [보완]

## 9. 기존 도구 조사와 반영점

| 도구 | 구조 요약 | 반영할 점 |
|---|---|---|
| AltTester | 게임 내 SDK + 중계 서버 + 다국어 드라이버(C#, Python, Java) | 러너를 중계 허브로 두는 현재 구조와 동일. 연결 방향을 설정 가능하게. 입력 주입을 Input 계층에서 처리 |
| Airtest Poco | 엔진별 SDK가 UI 계층을 공통 포맷으로 덤프, Python에서 셀렉터로 조작 | 엔진 무관 UI 계층 덤프 포맷, 정규화 좌표(0~1), 계층 뷰어 도구 |
| Unity Automated QA | 기록/재생, 기록에서 테스트 생성, 랜덤 크롤러. 2021.12 개발 중단 | 기록을 객체 기준 시퀀스로 저장, 크롤러 결과를 기록 파일로 남겨 테스트화 |
| GameDriver | 게임 내 에이전트 + HierarchyPath 쿼리 언어, 프로젝트 수정 없이 객체 식별 | 요소 식별의 기본을 쿼리 방식으로, ID 부여는 선택 사항으로 |
| 연구 동향 | 자동 버그 탐지 = 탐색 + 버그 식별. LLM 에이전트 탐색 사례 등장 | 계층 덤프 + 명령 프로토콜을 외부 탐색 에이전트가 쓸 수 있는 인터페이스로 설계 |

### 조사로 새로 생긴 결정 사항

- 드라이버 계층(요소 찾기, 클릭, 값 읽기, 기기 제어) 포함 전부 직접 구현 [확정]
  - 외부 도구에 의존하지 않음. 기존 도구는 설계 참고용으로만 사용
- 연결 방향: 둘 다 지원, 설정으로 선택 [확정]
  - 1차 구현: 게임(에이전트)이 기다리고 PC(러너)가 접속. USB 기기와 에디터용
  - 2차 구현: PC(러너)가 기다리고 게임(에이전트)이 접속. 클라우드 기기, 원격 기기용
  - 연결 방향과 무관하게 연결 이후의 메시지 처리는 동일하게 유지 [보완]
- 요소 식별: 조건 검색(이름, 타입, 텍스트, 계층 관계) 기본 + 고유 ID 선택 사용 [확정]
  - 이유: 기획자와 QA는 프로그래머가 아니어서 고유 ID를 직접 확인하기 어려움
  - 고유 ID 사용 여부는 사용자가 설정에서 결정 [확정]
  - 사전 검증기 제공 [확정]
    - 같은 조건에 여러 요소가 걸리는 중복 검출
    - 조건에 걸리는 요소가 없는 경우 검출
    - 검증 시점: 에디터에서 씬/프리팹 정적 검사 + 실행 중 화면 기준 검사 [보완]
    - 목록 아이템처럼 의도된 중복은 부모 범위나 순번으로 구분하는 표기 지원 [보완]
    - 중복 발견 시 구분 가능한 조건 제안 [보완]

## 10. 개념 구분: 테스트 케이스, 테스트 결과, 버그 리포트

| 개념 | 무엇인가 | 언제 생기나 | 수명 | 저장 위치 |
|---|---|---|---|---|
| 테스트 케이스 (TC) | 무엇을 어떻게 확인할지에 대한 계획 | 테스트 전, 사람이 설계 | 기능이 있는 동안 계속 유지 | 시트 (목록) + 규칙 파일 (실행 방법) |
| 테스트 결과 | 특정 빌드와 기기에서 TC를 한 번 실행한 기록 | 실행할 때마다 | 누적되는 이력 | 러너 리포트, 시트에는 최신 결과 표시 |
| 버그 리포트 | 발견된 문제 하나에 대한 보고와 처리 추적 | 문제가 확인됐을 때 | 고쳐서 닫힐 때까지 | 로컬 파일 + Jira/Notion |

- 관계 [보완]
  - TC 1개에 테스트 결과 여러 개 (빌드마다, 기기마다)
  - 실패한 테스트 결과가 버그 리포트로 이어질 수 있음. 단, 실패가 곧 버그는 아님 (환경 문제, 규칙 오류, 기획 변경 가능)
  - 버그 리포트는 TC 없이도 생김 (수동 테스터 제보, 크래시)
  - 버그가 고쳐지면 그 재현 스텝이 새 TC(회귀 테스트)가 됨
- 버그 리포트 표준 항목 [보완]
  - 제목, 재현 스텝, 기대 결과, 실제 결과, 심각도, 우선순위, 재현율, 빌드 버전, 기기와 OS, 증거(스크린샷, 영상, 로그), 상태, 연결된 TC와 테스트 결과
- TC 표준 항목 [보완]
  - 번호, 목적, 우선순위, 사전 조건, 입력(스텝), 기대 결과, 추적 정보(관련 기획이나 버그)
- 테스트 실패에서 버그 리포트로 가는 경로 [확정]
  - 자동 등록: 크래시, 처리되지 않은 예외, 프리징처럼 버그임이 분명한 것
  - 확인 대기: 규칙 실패(기대 결과와 실제 결과 불일치), 시각 검증 실패, 측정 예산 초과
  - 확인 대기 목록에서 사람이 "버그"로 판정하면 명령 하나로 버그 리포트 생성. 재현 스텝, 기대 결과, 실제 결과, 증거가 자동으로 채워짐
  - 사람이 내릴 수 있는 판정: 버그 / 규칙 오류 / 환경 문제 / 기획 변경 [보완]
  - "규칙 오류"와 "기획 변경" 판정은 해당 TC를 "규칙 갱신 필요"로 표시 [보완]
  - 확인 대기 목록의 조회와 판정도 CLI로 제공. AI가 1차 분류를 제안하고 사람이 확정 [보완]
  - 자동 등록 건도 중복 방지 규칙 적용 (5번 참고)
- 테스트 결과 보관: 종류별로 기한을 다르게 둠 [확정]
  - 모든 기한은 설정 파일에서 편집 가능. 항목별로 "무기한"도 선택 가능 [확정]
  - 종류별 구분과 기본값 (기본값은 조정 대상) [보완]

    | 종류 | 기본 기한 | 비고 |
    |---|---|---|
    | TC, 규칙 파일 | 무기한 | 저장소에서 Git으로 관리 |
    | 결과 요약 (통과/실패, 측정 수치) | 1년 | 용량이 작고 추이 분석에 필요 |
    | 통과한 실행의 스크린샷, 영상, 로그 | 14일 | 용량이 가장 큼 |
    | 실패, 불안정 실행의 스크린샷, 영상, 로그 | 90일 | 원인 분석용 |
    | 버그 리포트에 첨부된 증거 | 버그가 닫힌 뒤 90일 | 열려 있는 동안은 삭제하지 않음 |
    | "중요" 표시한 실행 | 삭제하지 않음 | 사람이 표시를 해제할 때까지 |

  - 사용자 정의(커스텀) 보관 규칙 [확정]
    - 기본 종류의 기한 값을 바꾸는 것뿐 아니라, 조건을 붙인 규칙을 사용자가 직접 추가 가능
    - 조건으로 쓸 수 있는 항목: 결과(통과/실패/불안정), 파일 종류(스크린샷/영상/로그), TC 우선순위, TC 태그, 빌드 종류, 기기 [보완]
    - 예: "우선순위 높음 TC의 실패 증거는 1년", "릴리스 후보 빌드의 결과는 무기한"
    - 여러 규칙이 겹치면 가장 긴 기한을 적용 [보완]
    - 위 표의 기본값은 아무 설정도 하지 않았을 때만 적용
  - 정리 실행 방식: 러너 실행 시 자동 정리 + 수동 정리 명령 [보완]
  - 삭제 전 미리 보기 명령 (무엇이 지워질지 목록만 출력) [보완]
  - 설정 조회와 변경, "중요" 표시도 CLI로 제공 [보완]
  - 용량 상한 설정: 기한 전이라도 상한을 넘으면 오래된 것부터 정리할지 [미정]
- 결정 필요 [미정]
